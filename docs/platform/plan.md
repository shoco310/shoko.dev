# 市民参加型政策プラットフォーム 調査報告と実装計画（提案）

作成日: 2026-11-20
位置づけ: **提案のみ。** この文書の作成にあたって、データベースの作成・外部サービスの契約・メール送信・本番デプロイは一切行っていない。

目指すサイクル: **市民の声を集める → 政策を改善する → 活動を公開する → 再び声を集める**

---

## 0. 結論（先に要点）

- 今のサイトは **GitHub Pages に置いた静的な React SPA**。サーバーもDBもないため、投稿・審査・メール通知には **バックエンドの追加が必須**。
- 推奨構成（2026-11-20 改訂）: **Vercel に移行する（Vite のまま。Next.js は使わない）。サーバー側 API は Vercel Functions（東京）、DB・認証は Supabase（東京）**。スパム対策は Cloudflare Turnstile、メールは Resend。ホスティングの比較と移行手順は [hosting.md](./hosting.md) にまとめた。
- **政策本文・変更履歴・統計データ・活動記録は、これまで通りリポジトリ内のデータ（`src/data/*.ts`）で管理する**。git の履歴がそのまま改訂の証跡になり、DB に入れる必要がない。DB に入れるのは「市民の投稿」と「公開用に書き直した課題」と「通知登録者」だけ。
- 個人情報は **非公開テーブルに隔離**。公開ページが読めるのは、スタッフが書き直して公開した課題だけ（DB 側の行レベルセキュリティで強制）。
- 開発順序: **A. バックエンド不要の改修 → B. 投稿＋受付番号＋審査画面 → C. 課題の公開と政策への紐づけ → D. メール通知 → E. AI**。
- 着手前に決めてほしいことは [§9](#9-着手前に決めていただきたいこと) にまとめた。特にメール通知は **公職選挙法・特定電子メール法の確認が終わるまで実装しない** ことを推奨する。

## 1. 現在の技術スタック・構成・デプロイ

### 技術スタック
| 項目 | 内容 |
|---|---|
| フレームワーク | React 18 + TypeScript 5（strict） |
| ビルド | Vite 5（`npm run build` = `tsc && vite build`） |
| アニメーション | framer-motion 11（`MotionConfig reducedMotion="user"` で動きを減らす設定に対応済み） |
| ルーティング | ライブラリなし。`App.tsx` で `#/policy/<slug>` だけを自前で判定するハッシュルーティング |
| スタイル | 単一の `src/styles.css`（約2,200行）。色・角丸・余白は `:root` の CSS 変数で管理（`--pink: #ff1680` など） |
| データ | `src/data/policy.ts`（4政策・統計・出典）、`src/data/activity.ts`（活動報告）をコードに直書き |
| 解析 | Google Analytics（`index.html` に gtag 直書き） |
| 外部フォーム | 後援会入会は Google フォーム、連絡は LINE公式・各SNS |

### ディレクトリ構成
```

src/
  App.tsx               … ハッシュルーティングと1ページ構成
  components/           … Header / Hero / Greeting / PolicySection / ActivitySection /
                          ProfileSection / SupportSection / ContactSection / Footer
  pages/PolicyDetail.tsx… 政策詳細（背景・取り組み・データ・課題・声・出典）
  data/policy.ts        … 政策データと型定義（DataPoint, SourceItem など）
  data/activity.ts      … 活動報告データ

docs/research/          … 政策調査レポート（作業中の資料）

```

### デプロイ
- `main` に push → GitHub Actions（Node 20、`npm ci` → `npm run build`）→ `dist/` を GitHub Pages に公開 → 独自ドメイン `shoko.dev`（CNAME）。
- **リポジトリは公開（public）**。秘密情報をコードやコミットに含めてはいけない。

### 調査中に気づいた点（今回の機能追加とは別）
- `node_modules/`（2,822ファイル）と `dist/` が git で追跡されている。CI で毎回ビルドしているので追跡は不要で、差分が見づらくなりレビューの妨げになる。→ タスク A-0 で追跡を外す。
- `index.html` の `og:image` が相対パス（`/images/ogp.jpg`）になっている。SNS によっては絶対 URL が必要。現在の本番では表示できている。

## 2. 既存のページと機能

| 画面 | URL | 内容 |
|---|---|---|
| トップ（1ページ構成） | `/` と `#message` などのページ内アンカー | Hero（キャッチ・LINE/後援会ボタン・SNS）→ ごあいさつ → 4つの政策 → 最新の活動 → プロフィール → 後援会のご案内 → お問い合わせ |
| 政策詳細 ×4 | `#/policy/education`, `#/policy/work`, `#/policy/childcare`, `#/policy/civic` | 背景と目指す姿 / 具体的な取り組み（既存制度バッジ付き）/ なぜ必要か / 数字で見る宇部の現状 / 調査結果から考えられること / 市民の声 / 関連資料・出典 / 他の政策 |

機能面:
- 入力を受け付ける機能はない（すべて外部の LINE・Google フォーム・SNS に誘導）。
- 政策ページは「一次資料で確認できた数値だけを出す」「議員・行政の発言を市民の声として扱わない」という方針がデータ型とコメントに組み込まれている。**この慎重さは新機能でも引き継ぐ**（公開課題・統計ページでも出典と確度を必須にする）。
- SNS リンク: Hero と お問い合わせ欄に X（https://x.com/shoko_sato_ube）を今回追加した（Instagram の前）。

## 3. サイトマップ変更案（現行デザイン・URL を維持）

方針:
- **既存 URL はすべて維持**（`#message` などのアンカー、`#/policy/<slug>`）。
- Vercel への移行後（M-2）は、新しいページを **パス形式（`/issues` など）** で作る。古い `#/policy/<slug>` はブラウザ側で `/policy/<slug>` に自動で置き換える（[hosting.md §5](./hosting.md#5-移行手順url-を壊さない方法)）。下の図ではパス形式で表記している。M-2 より前に作るページは、一時的に `#/…` 形式にする。
- 新しいページは既存の部品（`section-heading`、`btn--primary/secondary`、ピンク／白／黒の配色、`container--narrow`）を再利用し、見た目を揃える。

```
/（トップ・既存の1ページ構成）
├ Hero（既存）＋「困りごとを届ける」ボタンを追加
├ ごあいさつ（既存）
├ 4つの政策（既存）
├ ★ みんなの声（新しいセクション）… 公開済みの課題（新しい順に3件）＋ 投稿・一覧への導線
├ 最新の活動（既存）＋「調査・活動状況をすべて見る」リンク
├ プロフィール / 後援会 / お問い合わせ（既存）
└ フッター（既存）＋ 運営者表示・免責・プライバシーポリシーへのリンク

/policy/<slug>（既存。旧 #/policy/<slug> から自動で置き換え）
  └ 追加: 「この政策につながった市民の課題」「変更履歴」

★ /voice              困りごと・意見を送る（説明 → 入力 → 確認 → 送信）
★ /voice/done         受付完了（受付番号を表示）
★ /issues             公開中の課題一覧（テーマ・状況・関連政策で絞り込み）
★ /issues/<番号>      課題の詳細（要約・状況の経過・関連する政策）
★ /activity           活動・調査状況（既存の活動報告＋調査の進み具合）
★ /data               数字で見る宇部（宇部市の公式統計。出典と調査年を必ず表示）
★ /notify             メール通知の登録（フェーズD）
★ /notify/confirm     登録の確定（メール内リンクから開き、ボタンを押して確定）
★ /notify/stop        配信停止
★ /about              このサイトについて（運営者、政治活動のサイトであること、宇部市の公式サービスではないこと）
★ /privacy            プライバシーポリシー

（非公開）/admin/*      スタッフ用の審査画面（admin.html。公開サイトとは別のビルド入口。noindex・GA なし）
```

ヘッダーのナビ（現在6項目）には「みんなの声」を1つだけ追加し、項目が増えすぎないようにする。「困りごとを届ける」は Hero・みんなの声セクション・政策詳細の末尾に置く。

### 「4分類に無理に当てはめない」設計
- 投稿フォームでは**政策分類を選ばせない**。自由記述と、任意で選べる「近いテーマ」（子育て、交通、仕事、学校、医療・介護、まちづくり、その他／わからない など）だけを聞く。
- 公開課題には、政策（4分類）とは別に **テーマタグ** を持たせる。政策との紐づけは **0件でもよい**。一覧では「まだどの政策にも結びついていない課題」も同じように表示する。こうした課題は、政策を見直すきっかけとして見える形にしておく。

## 4. 推奨アーキテクチャ（2026-11-20 改訂：Vercel 移行）

詳しい比較・環境の分離・環境変数・RLS のチェックリスト・移行手順は **[hosting.md](./hosting.md)** を参照。ここでは要点だけを示す。

```
[市民のブラウザ]
   │  公開ページ（Vercel から Vite のビルド結果を静的配信）
   │
   ├─(投稿)──→ Vercel Function  POST /api/submit（Node.js, hnd1 = 東京）
   │             ├ Turnstile トークンをサーバー側で検証
   │             ├ 入力チェック・ハニーポット
   │             └ Supabase の RPC submit_voice()（secret key、サーバー側だけ）
   │                 → 回数制限の確認・submissions（非公開）に保存 → 受付番号を返す
   │
   └─(閲覧)──→ Supabase（publishable key）… 公開済みの課題だけ（RLS で制御）

[スタッフ]  /admin（admin.html。別エントリ）→ Supabase Auth（メールOTP＋TOTP 二段階認証）
             → RLS: is_staff() かつ aal2（二段階認証済み）の人だけが非公開データを読み書きできる

[メール（フェーズD）] Vercel Function → Resend（shoko.dev に SPF/DKIM/DMARC を設定）

環境: ローカル（Supabase CLI）／ Preview（Vercel Preview → Supabase staging）／ Production（shoko.dev → Supabase prod）
```

| 用途 | 採用するもの | 理由 |
|---|---|---|
| ホスティング | **Vercel（Vite のまま）** | プレビュー環境、環境ごとの秘密鍵、セキュリティヘッダー、パス形式の URL、デプロイが1系統で済む |
| サーバー側 API | **Vercel Functions（`api/`、Node.js、東京）** | 同じリポジトリと型を使える。秘密鍵をサーバー側だけに置ける |
| DB | **Supabase Postgres（東京）** | RLS で公開範囲を DB 自体に強制できる。データを日本国内に置ける |
| 認証（スタッフのみ） | **Supabase Auth（OTP＋TOTP）** | 市民側にはログインを求めない。一般の新規登録は無効にする |
| スパム対策 | **Cloudflare Turnstile**＋ハニーポット＋DB 側の回数制限 | 無料。画像選択パズルが出にくい |
| メール | **Resend** | 少量なら無料枠に収まる |

### 構成上の注意
- **審査画面は別エントリ（`admin.html`）にする。** 公開サイトのコードに審査画面のコードを含めない。`/admin/*` には `noindex`・キャッシュ禁止・GA なしを設定する。本当の防御は RLS が担う。
- **secret key は投稿受付の関数でだけ使う。** Vercel の Production と Preview に別々の値を Sensitive として登録する。`VITE_` で始まる名前にはしない（ビルド時に確認する）。
- **Supabase のライブラリは投稿・課題ページを開いたときにだけ読み込む。**
- **フォーム・審査画面では GA を読み込まない。** 関数のログにも投稿本文やメールアドレスを出力しない。

## 5. データモデル

### 管理の分け方
| データ | 置き場所 | 理由 |
|---|---|---|
| 政策本文・取り組み・出典 | `src/data/policy.ts`（既存） | 既存の仕組みのまま |
| **政策の変更履歴** | `src/data/policy.ts` に `changelog` を追加 | 変更とコード差分が同じコミットに入り、git の履歴がそのまま証跡になる |
| **統計データ** | `src/data/stats.ts`（新規）。既存の `DataPoint` 型を再利用 | 出典と調査年を型で必須にできる。人が確認してから載せる運用に合う |
| 活動報告 | `src/data/activity.ts`（既存）を拡張 | 既存の仕組みのまま |
| 市民の投稿・連絡先 | **DB（非公開）** | 個人情報を含む |
| 公開課題・進み具合・政策との紐づけ | **DB（公開用）** | 審査画面から更新するため |
| 通知登録者 | **DB（非公開）** | 個人情報を含む |

### DB のテーブル

```
── 非公開（スタッフだけが読める）──────────────────────
submissions                  市民の投稿（原文）
  id               uuid PK
  receipt_no       text UNIQUE    例 "UB-7KQ4-M2PX"（ランダム。連番にしない）
  body             text           本文（最大 4,000 字）
  theme_hint       text[]         任意で選ばれた「近いテーマ」
  area_hint        text           任意。地区レベルまで（住所は聞かない）
  age_range        text           任意（10代〜／回答しない）
  status           enum           received / reviewing / used / not_published / spam / urgent_referral
  reviewer_note    text           スタッフ用のメモ（公開しない）
  privacy_version  text           同意したプライバシーポリシーの版
  ip_hash          text           回数制限用（ソルト付きハッシュ。生の IP は保存しない）
  created_at, updated_at

submission_contacts          連絡先（投稿本体と分けて保存。必要がなくなったら削除）
  submission_id    uuid PK FK
  name             text   任意
  email            text   任意
  reply_ok         bool   「返信してもよい」に明示的に同意したか
  delete_after     date   保存期限（例：対応を終えてから6か月）

staff                        スタッフ（当面は佐藤祥子のみ。admin）
  user_id          uuid PK（auth.users）
  role             enum   admin / reviewer
  display_name     text

audit_log                    操作記録（誰が・いつ・何を）
  id, actor, action, target_table, target_id, at, detail jsonb

── 公開用（status = 'published' の行だけ一般に公開）──
public_issues                公開する課題（スタッフが個人情報を除いて書き直したもの）
  id               serial PK      公開番号（/issues/12）
  title            text
  summary          text           書き直した要約（原文をそのまま転載しない）
  themes           text[]         テーマタグ（政策分類とは別）
  progress         enum           heard（受け止めた）/ researching（調査中）/
                                  in_policy（政策に反映）/ proposing（提案・質問した）/ closed
  status           enum           draft / published / archived
  published_at, updated_at

issue_sources                公開課題と投稿の対応（非公開）
  issue_id, submission_id         ※ 公開ページには件数だけを出す

issue_policy_links           公開課題と政策（0件でもよい）
  issue_id, policy_slug text, note text, linked_at
  ※ policy_slug は policy.ts の slug と同じ値。ビルド時に整合性をチェックする

issue_updates                課題ごとの経過（活動・調査状況）
  id, issue_id, body, created_at, published bool

── 通知（フェーズD）────────────────────────
subscribers
  id, email, status (pending/confirmed/unsubscribed),
  confirm_token_hash, unsubscribe_token_hash,
  consent_text_version, consented_at, confirmed_at, unsubscribed_at
  topics text[]   （例：issue_updates / policy_changes / activity）

mail_sends                   配信記録（誰が承認して、いつ・何通送ったか）
```

### RLS（行レベルセキュリティ）の方針
- `anon`（一般の閲覧者）: `public_issues` と `issue_updates` と `issue_policy_links` は、**公開済みの行だけ** SELECT できる。それ以外のテーブルは一切読めない。INSERT もできない（投稿は Vercel Function `/api/submit` 経由に限る）。非公開テーブルからは GRANT も取り消す。
- `reviewer`: 投稿と公開課題を読み書きできる。`submission_contacts` は画面上では伏せ字にし、「表示」を押したときだけ見られる。その操作は audit_log に記録する。
- `admin`: 上記に加えて、スタッフ管理・メール配信の承認・データの削除ができる。
- RLS のテストを CI で自動実行する（anon で非公開テーブルを読めないことを毎回確認する）。

### 受付番号
- 形式は `UB-XXXX-XXXX`（紛らわしい文字を除いた英数字のランダム値）。連番にしないのは、投稿件数を推測されたり、他人の番号を当てずっぽうで調べられたりしないようにするため。
- MVP では **受付番号だけで状況を照会する機能は作らない**。番号は「お問い合わせのときにお伝えください」という用途に限る。照会機能を作る場合は、番号に加えて別の秘密情報（照会用のコードやメール確認）を必須にする。

## 6. 運用ルール（設計上の重要事項への対応）

**運営者と責任（2026-11-20 確定）:** サイトの運営者は佐藤祥子本人（後援会の代表も本人）。サイトは佐藤祥子個人の政治活動・政策発信サイトとして位置づける。個人情報の管理責任者、および市民投稿の管理・審査・公開の判断者は佐藤祥子とする。

| 要件 | 対応 |
|---|---|
| 原則非公開で受け付け、人の審査を経て公開する | 投稿は submissions に保存するだけ。公開用データ（public_issues）は、**スタッフが要約を書き直して作り、公開ボタンを押したときだけ**表示される。原文を自動で公開する経路は作らない |
| AI による自動公開・自動的な政策判断をしない | フェーズE でも、AI は「下書き・個人情報の候補検出・似た投稿の提案」だけを行う。公開と政策への反映は必ず人が判断し、audit_log に担当者を残す |
| 個人情報と公開情報を分ける | テーブル・権限・画面の3段階で分ける。公開用の要約は書き直す（固有名詞・地区より細かい場所・個人を特定できるエピソードを除く）。審査画面に公開前チェックリストを表示する |
| メール通知は明確な同意がある人だけ | 投稿時の「返信してよい」と「お知らせを受け取る」は**別々のチェック欄**にし、初期状態はどちらもオフ。登録は二重確認（確認メールのリンク → 開いたページでボタンを押して確定）。リンクを開いただけでは確定しない（メールのセキュリティスキャナーが自動でリンクを開いても登録されないようにするため）。すべてのメールに配信停止リンクを入れる |
| 政治活動のサイトであることを明示する | フッター・投稿フォームの冒頭・送信完了画面・/about に表示する: 「このサイトは佐藤祥子（さとうしょうこ）が運営する、個人の政治活動・政策発信のためのウェブサイトです。宇部市の公式サイト・行政サービスではありません。行政への正式な申請・相談は宇部市の窓口へ」（フッターと /about で実装済み） |
| 緊急の相談への対応 | フォームの冒頭に「命や安全に関わる緊急のご相談は 110番・119番、または市や県の相談窓口へ」と表示し、窓口のリンクを載せる。審査で緊急性があると判断した投稿は `urgent_referral` にし、対応手順を決めておく |
| 返信・対応の約束 | 「すべての投稿にお返事できるとは限りません」と明記する（期待とのずれを防ぎ、運営の負担を抑える） |
| スパム対策 | Turnstile、ハニーポット欄、IPハッシュ単位の回数制限（例：1時間に3件まで）、文字数の上限、URL を多く含む投稿の自動判定（`spam` 候補に分類するだけで、削除はしない）、ファイル添付は MVP では受け付けない |
| アクセシビリティ | すべての入力欄にラベルを付ける。エラーは文章で示す（色だけに頼らない）。キーボードだけで操作できるようにする。確認画面で入力内容を見直せるようにする。文字数カウンターを付ける。既存の reduced-motion 対応を維持する。WCAG 2.2 AA を目標にする |
| 運営の負担 | 審査は「一覧 → 詳細 → 状態の変更」の3操作で済むようにする。新しい投稿の通知はスタッフ宛てに1日1回まとめて送る。保存期限を過ぎた連絡先を自動で削除するジョブを用意する |

### 法令面で確認が必要な点（実装前に専門家または選挙管理委員会へ確認することを推奨）
- **公職選挙法**: 選挙期間中に電子メールで選挙運動ができるのは候補者・政党等に限られ、送信先にも制限がある。告示前の事前運動も禁止されている。通知メールの内容は「活動報告」にとどめ、投票の呼びかけを含めない運用ルールが必要。投票日当日のサイト更新の扱いも確認する。
- **特定電子メール法**: 同意の記録（いつ・どの文面に同意したか）を保存し、送信者名・住所・配信停止方法をメールに必ず表示する。→ `consent_text_version` と `consented_at` で記録する。
- **個人情報保護法**: 利用目的、委託先（Vercel・Supabase・Resend・Cloudflare）、保存期間、開示・削除の請求窓口を /privacy に明記する。海外の事業者を利用する場合は、外的環境の把握についても記載する。
- **Google Analytics** の利用もプライバシーポリシーに記載する。

## 7. 既存機能への影響と移行リスク

| リスク | 影響 | 対策 |
|---|---|---|
| 静的サイトからバックエンドありの構成になる | 障害が起こりうる箇所・費用・保守が増える | 公開ページは静的配信のまま。DB が止まっても既存ページ（政策・活動・プロフィール）は表示され続ける構成にし、投稿と課題一覧だけが「一時停止中」と表示されるようにする |
| ルーティングの変更 | 既存の `#message` などのアンカーや `#/policy/…` が壊れるおそれ | 今の「該当しなければ1ページ構成を表示する」挙動を保ったまま判定を一般化する。既存 URL の表示テストを追加する |
| 公開リポジトリ | 秘密鍵が漏れるおそれ | service_role キーは Supabase のシークレットにだけ置く。`.env*` を ignore する。シークレットスキャンを有効にする |
| 個人情報の漏えい | 最も重大なリスク | RLS ＋ CI での権限テスト、二段階認証、操作記録、伏せ字表示、保存期限での自動削除、エクスポート機能を作らない |
| 公開内容から個人が特定される | 小さな地域なので、要約からでも特定されうる | 書き直しを必須にし、チェックリストを使う。地区より細かい場所・年齢と家族構成の組み合わせなどを避ける。将来スタッフを追加した場合は、公開前に2人目が確認することを推奨 |
| 表示速度の低下 | 現状の JS は約310KB（gzip後 約103KB） | Supabase のライブラリは遅延読み込みにし、トップページには読み込まない |
| ホスティングの移行 | DNS を切り替える間に表示できなくなる、またはハッシュ URL が壊れるおそれ | Vercel への移行は市民参加機能とは別のブランチ・コミットで進める。DNS を切り替える前に TTL を短くし、GitHub Pages を残して切り戻せるようにする。ハッシュ URL はブラウザ側で自動的に置き換える（[hosting.md §5](./hosting.md#5-移行手順url-を壊さない方法)） |
| 検索エンジンへの露出 | ハッシュ URL は検索結果に出にくい | M-2 でパス形式の URL に移行し、ページごとの HTML（OGP）をビルド時に生成する |
| 運営の負担 | 投稿が多いと審査が追いつかない | 告知の範囲を段階的に広げる。返信をお約束しないと明記する。審査の状況を週1回確認する |
| node_modules・dist の追跡 | 差分の確認が難しい | A-0 で追跡を外す（本番の表示には影響しない） |

## 8. MVP と開発順序

### 移行トラック M（ホスティング。市民参加機能とは別のブランチ・コミット）
M-1 `vercel.json` の追加と追跡不要ファイルの整理（`chore/vercel-migration` で実施済み）→ Vercel プロジェクトの作成とプレビューでの確認 → **DNS 切り替え（事前に確認をいただく）** → GitHub Pages の停止 → M-2 パス形式の URL への移行。詳細は [hosting.md](./hosting.md)。

### フェーズA：バックエンドなしでできる改修（リスクが低いので先に公開）
| # | タスク | 主な変更 |
|---|---|---|
| A-0 | （M-1 で対応済み）`node_modules/`・`dist/` の追跡を外し、`.gitignore` に `.env*` を追加 | — |
| A-1 | ルーターを一般化する（既存のアンカーと `#/policy/…` はそのまま動かす）。M-2 の後はパス形式の URL に対応し、ハッシュ URL を置き換える処理もここに入れる | `App.tsx`、`src/router.ts`（新規） |
| A-2 | /about（運営者・免責）と /privacy を追加し、フッターに表示とリンクを追加する | `pages/About.tsx`、`pages/Privacy.tsx`、`Footer.tsx` |
| A-3 | 政策の変更履歴: `Policy.changelog[]`（日付・概要・理由・関連課題）を追加し、詳細ページに表示する | `data/policy.ts`、`PolicyDetail.tsx` |
| A-4 | /data 数字で見る宇部: 政策ページに掲載済みの確認済みデータを集めて表示する。新しい数値は `docs/research` で一次資料を確認してから追加する | `data/stats.ts`、`pages/Data.tsx` |
| A-5 | /activity 活動・調査状況: 既存の活動報告に加え、調査の進み具合（調査中・確認済みなど）を表示する | `data/activity.ts`、`pages/Activity.tsx` |

### フェーズB：投稿の受付と審査（MVP の中心）
| # | タスク |
|---|---|
| B-1 | Supabase の `shoko-staging`・`shoko-prod`（東京）とローカル環境（Supabase CLI）を用意し、Vercel の Preview／Production に環境変数を登録する。マイグレーション（テーブル・RLS）をリポジトリの `supabase/migrations/` で管理する ※**契約・作成は承認後に行う** |
| B-2 | RLS のテストを作り、CI で実行する（anon で非公開データを読めないことを確認） |
| B-3 | Vercel Function `api/submit.ts` と Supabase RPC `submit_voice()`: Turnstile の検証・入力チェック・回数制限・受付番号の発行 |
| B-4 | /voice フォーム（説明 → 入力 → 確認 → 送信）と /voice/done（受付番号を表示） |
| B-5 | admin.html: ログイン（OTP＋二段階認証）、投稿一覧、詳細、状態の変更、メモ、連絡先の伏せ字表示、操作記録 |
| B-6 | 連絡先を保存期限で自動削除するジョブ、スタッフへの1日1回のまとめ通知 |
| B-7 | 限られた人だけに公開して試験運用し（後援会の内部など）、その後に一般公開する |

### フェーズC：課題の公開と政策への紐づけ
| # | タスク |
|---|---|
| C-1 | 審査画面: 投稿から公開課題を作成する（書き直しの入力欄・公開前チェックリスト・プレビュー・公開ボタン） |
| C-2 | /issues 一覧（テーマ・状況・関連政策で絞り込み、「まだ政策に結びついていない課題」も表示）、/issues/<番号> 詳細（経過を時系列で表示） |
| C-3 | 政策詳細に「この政策につながった市民の課題」を追加。変更履歴（A-3）から関連する課題へリンクする |
| C-4 | トップに「みんなの声」セクションを追加し、Hero などに「困りごとを届ける」ボタンを追加する |

### フェーズD：メール通知（法令面の確認が終わってから）
- D-1 Resend の契約、shoko.dev の SPF/DKIM/DMARC 設定
- D-2 /notify の登録・確定・配信停止（二重確認）
- D-3 審査画面から配信する（下書き → admin の承認 → 送信。自動送信はしない）
- D-4 投稿者への返信（`reply_ok` の人だけ。テンプレートを用意する）

### フェーズE：将来の機能（MVP 外）
- e-Stat API などを使った統計データの半自動更新（取得した値は人が確認してから反映する）
- `/issues/<番号>` を SNS でシェアしたときのプレビュー表示（Vercel Function で OGP を動的に生成する）
- **AI**: まずスタッフ向けの補助（要約の下書き・個人情報の候補検出・似た投稿のまとめ）から始める。市民向けの「AI 政策対話」は、公開済みの政策・課題・出典だけを根拠に、出典付きで答える形にする。AI であることを明示し、会話内容を保存するかどうかは利用者が選べるようにする。外部の AI API には個人情報を除いたデータだけを送る

### MVP の範囲
**A（全部）＋ B ＋ C-1〜C-3** を MVP とする。「声を集める → 審査する → 課題として公開する → 政策と変更履歴につなげる」という一周が、メール通知なしで回る状態。メール（D）はその次に回す。

## 9. 着手前に決めていただきたいこと

1. **インフラ**: Vercel ＋ Supabase で決定（2026-11-20）。Vercel のプラン・Supabase の組織・DNS については [hosting.md §8](./hosting.md#8-決めていただきたいこと) を参照。
2. **審査する人**: 決定（2026-11-20）。運営者の佐藤祥子が、投稿の管理・審査・公開と、個人情報の管理責任を担う。スタッフを追加する場合も、公開の最終判断は佐藤祥子が行う。
3. **連絡先の保存期間**: 例「対応を終えてから6か月」でよいか。
4. **受付番号での状況照会**: MVP では作らない案でよいか。
5. **法令面の確認**: メール通知（フェーズD）の前に、選挙管理委員会または専門家に確認できるか。
6. **公開の順序**: フェーズA を先に単独で公開してよいか。

## 参考にした仕組み（デザインや実装はコピーしない）
- **チームみらいの政策参加の取り組み**: 政策文書を公開して変更履歴を追えるようにし、市民の意見を受けて改訂する考え方。→ 本計画では「政策の変更履歴を git とサイトの両方で公開し、きっかけになった課題へリンクする」形で取り入れた。
- **OutSystems のアワード応募・管理システムのような仕組み**: 応募 → 受付番号の発行 → 非公開での審査 → 状態の管理 → 結果の公開、という流れ。→ 投稿・審査（フェーズB）の画面の流れに取り入れた。
